# 夜間の不具合修正手順（Claude 用）

毎晩 1:00 頃（日本時間）に起動する Claude のセッションは、この手順だけを行う。
**本番への反映・マージ・承認は絶対に行わない。** 反映は所有者が `approved` ラベルを付けた PR だけを、
2:00 の `Nightly release` ワークフローが行う。

## 対象

- リポジトリ `sukesuke1024-lgtm/Trading-overseas` の open Issue のうち、ラベル `bug` が付いたもの
- 既に修正案 PR（本文に `Fixes #番号` を含む open PR）があるものは対象外
- `needs-info` ラベルが付き、その後に新しいコメントがないものは対象外
- 1 晩に扱うのは最大 3 件（古い順）

## 手順

1. Issue の内容（画面・エラー・スタック・再発コメント）を読み、`aitrek-os/` のコードで原因を特定する
2. 原因を特定でき、修正範囲が小さく安全だと判断できる場合のみ修正する
   - 既定ブランチから `fix/issue-<番号>` ブランチを作る
   - 修正は不具合の原因に対する最小限の変更にする（ついでの改善・リファクタリングはしない）
   - `aitrek-os/src/lib/changelog.ts` と `package.json` のバージョンは変更しない（反映時に自動で記録される）
   - 次を実行し、すべて成功することを確認する：`cd aitrek-os && npm ci && npm run lint && npm run typecheck && npm run build`
   - 可能なら Playwright で該当画面の再現・修正後の動作を確認する（`/opt/pw-browsers` のブラウザを使用）
3. PR を作成する
   - base：既定ブランチ、ラベル：`fix-proposal`（`approved` は付けない）
   - タイトル：不具合の内容が分かる日本語（例：「Deal 詳細で数量が 0 になる不具合を修正」）。このタイトルがそのまま更新履歴に載る
   - 本文（日本語）：`Fixes #番号`、原因、修正内容、影響範囲、確認した内容、残るリスク、所有者が確認すべき点
4. 原因を特定できない・修正が大きい・仕様判断が必要な場合は修正しない
   - Issue に調査結果と、所有者に判断してほしい点をコメントし、`needs-info` ラベルを付ける
5. 最後に、その晩の結果（作成した PR、見送った Issue と理由）を 1 つの Issue コメントにまとめる必要はない。各 Issue / PR に記録が残っていればよい

## 禁止事項

- PR のマージ、`approved` ラベルの付与・削除、既定ブランチ・`production` ブランチへの直接 push
- テストや lint の無効化、チェックを通すためだけの変更
- 秘密情報（API キー等）の追加、`.github/workflows/` の変更（不具合が workflow 自体にある場合は Issue にコメントして所有者に委ねる）
- 本番データ・Supabase への接続や変更
- Issue に取引データ・個人情報を書くこと
